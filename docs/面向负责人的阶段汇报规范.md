# 面向负责人的阶段汇报规范

本规范用于项目负责人阅读的阶段进度、架构和交付汇报。先让读者理解交付范围和整体结构，再在结构发生变化的位置展开重点，最后给出验证与范围边界。执行记录、独立审查和 Agent 交接仍保留各自的组织方式和既有要求。

## 适用与存放

- 阶段汇报按日期和阶段分别存放，主线基线名称采用 `YYYY-MM-DD-Mn.0进度与架构图.md`；不把新阶段的进度混入旧阶段页面。
- 独立补充工作沿当前主线实现基线编号为 `Mn.1`、`Mn.2`，文件名使用同一规则。Console 全屏 TUI 的 M2.1 和已建立的 M3.1 保留历史编号；建立新主线实现报告后，后续独立补充沿新基线编号。候选计划不改变当前补充编号。
- 主线候选计划不改变补充编号。补充页开头单列主线实现/验收状态和下一阶段设计状态，不因界面增量或补充自验通过扩大主线交付结论。
- `docs/` 页首继续保留实际代码 Owner。开头写明阶段、基线日期、覆盖范围和当前状态，并链接上一阶段；后补复核注明发生日期。
- 本规范是面向人的阅读结构，不取代计划、源码、测试、独立 Review 或最终验收。代码事实对照源码，历史结果对照当时的记录。
- 不将所有日志复制进汇报。正文提炼结论、结构、重点和证据，原始过程通过链接追溯。
- 独立工作线的“尚未完成的整体结构 / 验证记录 / 范围边界”只记录本线拥有的结构、证据与范围。主线状态只作为开头基线或依赖背景，不在后三节扩展为全局状态表。
- 简短的聊天答复按同一阅读顺序提炼关键结论并链接阶段页，无需机械展开全部章节；完整阶段文档按下述顺序组织。

## 固定阅读顺序

| 顺序 | 章节 | 必须回答的问题 |
| --- | --- | --- |
| 1 | 交付范围 | 本次交付什么、用于什么场景、目前到哪个状态？ |
| 2 | 简化总图 | 整个系统由哪些功能块协作？ |
| 3 | 组件关系 | 模块由谁拥有、通过什么接口协作、对应哪些实现？ |
| 4 | 相比上一阶段增加了什么（适用时） | 总图中的哪一块发生了结构变化，为什么需要变化？ |
| 5 | 详细关系 | 各条局部调用、数据流和控制路径如何运行？ |
| 6 | 专项报告 | 本次最需要理解的周期、边界、记录、上下文、调用或输出保证是什么？ |
| 7 | 尚未完成的整体结构（适用时） | 明确声明的目标中还剩什么，影响哪条路径，归属哪一批交付？ |
| 8 | 验证记录 | 自验、独立审查、修复复核、人工验收各有什么证据与未验证项？ |
| 9 | 范围边界 | 本阶段明确延后或排除什么，不承诺什么？ |

条件章节不为凑齐标题而创建。首个基线没有上一实现阶段时，省略增量章节；没有剩余结构工作时，省略“尚未完成的整体结构”。不同阶段仍保持其余章节的名称和相对顺序。

## 各章节的内容要求

### 交付范围

用明确能力和可验证场景概括本次交付。区分本期实现、继承能力和后续目标；文件新增数量、步骤拆分或代码清理不能单独作为架构交付结论。实现完成、自验通过、独立审查完成、修复复核通过和负责人验收分别表述。

### 简化总图

只画主要功能块和它们的协作关系，不展开文件、方法、每次返回、装配注入与异常路径。总图应先于局部图出现，后面的局部图沿用总图的模块名称。箭头含义在图旁写清楚。

### 组件关系

解释模块的所有权、公共接口、部署/进程边界、装配方式和实现位置。可使用分组图或表格，避免重复总图。区分生产实现、测试替身、只完成注入的对象与尚未实现的规划组件。

### 阶段增量：先定位，再局部展开

这是后续阶段的重点章节，必须建立在上一阶段的结构上：

1. 明确对照基线及其日期，不把当前源码的能力倒写到历史基线。
2. 指出简化总图中变化所在的节点、边界或连接；必要时给总图该部分着色或编号锚点。
3. 就地展开这一块，画修改前/后的局部结构，标明新增、替换、拆分、合并和沿用关系；其他模块收起为未变化的协作者。在“修改后”的位置展开新增模块的调用、关键数据和实际控制关系，改动较小时可直接使用文件/方法粒度，进一步抽象由实际修改范围决定。
4. 说明职责、所有权、接口和使用行为怎样改变，以及旧入口/旧实现如何保留或迁移。
5. 将其余变化用短表补充。若存在多个独立重点，逐块展开，不重新画一张所有关系混杂的大图。

不能仅用“新增几个文件”“拆出执行步骤”或一条流水线说明阶段增量。读者应能从整体定位变化，再理解这块为何展开、展开后由谁负责什么。

独立新增的触发来源或生命周期机制应单独指出，即使复用了同一个执行器。例如 Heartbeat 的新增要分别说明来源拥有者、启停、唤醒入口和积压处理，不能只藏在“新增来源”节点或接口表中。

### 详细关系

每图只讲一个主题，例如接入调度、模型/工具往返、事实写入、公开诊断、生命周期停止、兼容路径或装配。调用返回适合时序图，所有权适合分组图，静态职责适合表格。装配、正常数据流和停止控制不叠画。

节点写短职责名，文件名和参数放在图旁的对照表。循环、失败、取消或 unknown 只在相关局部图展开，不回填到总图。图下解释必要的保证和限制，不逐条复述箭头。

### 专项报告

只选本次改动的重点，用二级章节“专项报告”和三级主题组织；主题数量按实际需要决定。每个主题说明机制、对外保证、失败边界及证据入口。图已经说明的顺序不再完整重复。

专项主题尚未确定且负责人要求留位时，正文保留“待添加”。模块逻辑与复杂度说明放在对应结构展开处，不用这些内容代填专项。

重大决策允许增加篇幅和局部图的复杂度。应展开当前采用的契约和具体机制、选择理由、代价与故障边界、源码/验证证据，以及后续目标。队列和执行器需要说明内部状态及提交责任，不能只写“单一 FIFO”或“单一执行器”标签。保持分主题展开，不因内容增加重新合并成全量关系图。

讨论目标、已确认决定、实际实现和后续方案分别标明。出现差距时对照原目标与代码现实，说明影响、后续归属和验收条件；公开了限制不等于已经落实原目标。未来工具或流程图明确标为示意和未实现，候选接口/参数不写成已经冻结的契约。

可选主题包括运行周期与身份、生命周期/取消、存储提交、上下文容量、调用配对、外部效果和公开输出。数值给单位、默认值和适用范围，不把软目标写成硬保证，不把诊断通知写成存储确认。

### 尚未完成的整体结构

按“缺口、当前事实、归属本期或后续、影响、下一步”列出；区分本期漏交、待实现结构与明确延后范围。延后能力不能成为无限阻塞本期完成的隐含条件，纯粹的待 Review/验收状态列在验证记录。

完成条目从当前汇报移除，证据保留在原任务/审查记录。本阶段完成后删除该章节，剩余后续目标归入范围边界或下一阶段规划。历史记录的 append-only 要求不因此改变。

### 验证记录

自验执行后先记录已有证据，独立审查和修复复核后继续补齐；不等审查才列验证，也不提前宣称审查通过。至少区分自动化、手动样例、协议替身、真实服务、独立审查、修复复核和负责人验收。

写明日期、验证对象、结果、覆盖边界与证据文件。测试数量绑定当时版本；语法检查与真正类型检查、协议替身与联网往返分别记录。未知的审查人、日期或结论不编造；来源仅为负责人确认时明确说明。

复原旧阶段时，先读计划、任务与归档，再对照实际实现；已被后续 Update/Correction 替代的计划不能写成最终事实。当前执行的新测试不用于替代历史测试数。

### 范围边界

集中列出本阶段排除、延期和不承诺的能力，链接相关决定或后续计划。范围变化注明当前依据，不将历史建议写成冻结决定。已确认延后项不作为本期漏交，未实现组件不画作已存在对象。

## 图形与阅读检查

- 先总图，再结构增量，再局部细节；一图只使用一种主要关系语义。
- 普通功能图尽量不超过 9 个节点；局部时序图尽量不超过 5 个参与者，超出时优先拆分。
- 新增/沿用/替换用一致的颜色和明确文字标识，不能只依赖颜色传递含义。
- 优先减少标签和连线，不靠缩小字体容纳复杂图；以约 800 px 阅读区检查宽度和可读性。
- 新增或实质调整图后实际渲染并查看截图，检查交叉、遮挡、裁切、文字大小和箭头方向。使用本地资源验证，避免第三方脚本获得内部文档并联网；无法验证时明确报告限制。
- 对照源码和历史证据核对每个节点及关系，不为了图形对称而添加不存在的调用。
- 发布前检查章节顺序、Owner、阶段间术语、时间/验收状态、文件链接和所有声明的证据。

## 与既有文档要求并行

`AGENTS-en.md` 关于简洁写作、代码所有权、计划/任务位置、追加记录、历史保留、测试、独立 Review 和归档的要求继续生效。代码注释的英文结构锚点和中文审查说明约定继续生效。

计划保存范围、设计与实施安排，不作为进度或验收记录更新。执行进展、验证、审查和验收结论写入任务记录或本规范组织的阶段报告；只有负责人明确要求调整范围或设计时才修改计划。计划原文保持，归档位置记录在任务文件。

Agent 交接文档可以按执行依赖、步骤和待办组织；任务记录与日志可以保持时间顺序；审查报告可以按发现、位置、影响和复现证据组织。它们是阶段汇报的证据来源，无需重排为本文目录，也不能用它们的流水记录替代面向负责人的结构说明。
