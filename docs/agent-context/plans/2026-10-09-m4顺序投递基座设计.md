# M4 顺序投递基座设计

## 已确认范围

M4 仅交付 World 顺序投递/长期去重、保存与结清确认、新实例进度重建和诊断、有界运行视图及兼容迁移。任务状态与心跳任务延续独立延后；不建设持久原始 ID 索引、滑动去重窗口或 fsync 确认路线。

accepted 继续在内存受理后返回。接收追加确认后才能执行，终态追加确认后才能结清。FIFO、固定输入边界、取消/停止、旧代 sink 失效、unknown 停止和诊断优先保留。未完成任务、积压事实和工具动作不自动补投或重放。

## 来源契约与身份

### 注册身份

Runtime 从装配读取有限的流声明，归属于当前 World.id 和 Session。每条声明绑定 streamId 与稳定 epoch；World 不能靠 Event.source 标签新增来源。首次注册先保存控制记录，再开放相应投递口；重启已有声明必须与保存的绑定一致。

首版每个流只支持一个已登记 epoch，恢复同一 epoch，不提供运行中动态注册/换代。来源进程重启也沿用 epoch 和序号；配置不一致返回明确诊断，不自动清空进度或注册新世代。以后增加来源换代时再设计旧流退休和跨代事实关系。此限制符合首版保持核心轻量的范围。

去重范围为一个 Session 内已登记的 `(World.id, streamId, epoch, sequence)`。Runtime 生命周期 generation 只管理本次连接/提交权，不进入长期来源身份。不同 Session 没有全局去重保证；来源重连必须保持目标绑定，Runtime 不通过自动新建 Session 继续重投旧事实。

### 投递信封

建议新增独立的 WorldDelivery，保留原 Event，外带 streamId、epoch、sequence 和可选 expiresAt。World.id 与 Session 由投递口绑定，不由信封自报。

| 字段 | 契约 |
| --- | --- |
| streamId | 装配认可的逻辑流，同一来源可以有少量独立流 |
| epoch | 该流稳定的序列世代；不会随 Runtime 或生产者重启随机改变 |
| sequence | 从 1 开始的连续正安全整数；拒绝越界，不自动绕回或换代 |
| event | 原始业务事实；id、source、occurredAt 和 payload 保持领域含义 |
| expiresAt | 首次受理时固定；未声明不按 occurredAt 年龄过期 |

同一投递身份的事实与有效期不变。来源重投保留原信封；活动区间的同身份冲突明确拒绝，不替换已受理副本。旧前缀重复只证明该位置已有保存/结清事实，若需要核对旧内容，使用事实查询，不能根据水位伪造历史结果。

World triggerId 编码明确区分 ordered 与 legacy 入口命名空间，ordered 再使用投递元组；原 Event.id 保留。取消、快照和诊断使用回执中的 triggerId；原事件 ID 可以在不同流相同，不能再用 Event.id 作为所有 World 投递的唯一键。编码规则由协议实现统一提供，不拼接未经转义的标签，也不靠猜测某字符串是否已编码来混用旧/新 ID。

queueSequence 仍表示 Runtime 实例内混合来源的受理顺序；Session 位置表示记录位置；两者都不能当作上游稳定 sequence。

### World 适配器必须承担的工作

适配器在首次投递前取得或保存稳定序号与事实，保留未确认项。Runtime 拒绝、连接中断或未收到保存确认时，仍保留并按原序号重新投递。保存确认后可以按选定存储等级释放事实副本，但必须保留能延续原序列的进度/关联依据，不能在下次启动从 1 重新计号。

平台已有可恢复游标时可直接适配；没有时由适配器的持久发件记录建立序列。仅在每次调用 sink 时分配新序号，无法去重重复投递。若平台没有稳定原始身份，适配器不能证明重复采集为同一事实；核心只承诺符合来源契约的投递去重。

M4 用一个真实本地发件记录的测试 World 验证此责任，持久化事实/序号以及确认进度，实际重建生产者对象或子进程。它是测试夹具，不预建通用平台消息服务；生产 World 另选。

## 受理状态与三个水位

每流维护以下标量及有限未压缩区间：

| 状态 | 含义与确认依据 |
| --- | --- |
| admittedTail | 当前实例已占用的最大连续来源序号，包含接收写入等待；仅内存事实 |
| receivedPrefix | 连续接收保存前缀，接收追加成功后推进；从 Session 重建 |
| settledPrefix | 连续终态结清前缀，run_finished 追加成功后推进；不等于业务成功 |
| 待压缩区间 | settledPrefix 之后已受理的位置，保存接收 Promise、状态及必要关联；条数有上限 |
| 阻塞诊断 | 未结清、unknown、悬空调用、存储错误、登记冲突等；不因水位推进消失 |

必须保持 `settledPrefix <= receivedPrefix <= admittedTail`。首个合法序号为 1，初值为 0。单一追加链使接收前缀可连续确认；终态可能因排队取消/过期乱序提交，只能连续推进。

### 提交判断顺序

先验证实际外部边界的形状、容量、流绑定与生命周期，再检查重复或缺口，然后检查队列与待压缩容量。内部使用已成立的类型/登记契约，不重复校验每个字段。

| sequence 与状态 | 回执与行为 |
| --- | --- |
| 位于保存/结清前缀 | duplicate，返回对应保存/结清阶段，不再入队或追加接收事实 |
| 在 admittedTail 内尚未保存 | duplicate/admitted，关联原项的保存等待，不分配新队列序号 |
| 等于 admittedTail + 1 | 容量满足则 accepted；保存副本、占位、入队、立即启动接收追加 |
| 大于 admittedTail + 1 | sequence_gap，携带 expectedSequence；不占位、不缓冲、不改水位 |
| epoch 或绑定不符 | 明确拒绝，不自动创建新来源 |
| 队列或未压缩区间满 | queue_full 或 delivery_window_full；不占位，来源保留事实 |

duplicate 是原投递的查询结果，不是第二次 accepted；对活跃项保留必要关联，对很旧的已结清项可以只返回阶段/水位。完整业务结果只能来自历史记录，不能制造“重复即 succeeded”。

合法新项的占位、队列序号与接收追加启动在通知监听器前完成，保留 M3 重入顺序。执行仍等待本项接收追加，再检查取消/有效期并进入 TriggerRun。来源重投改变 source 文本、Event.id 或时钟，不改变登记身份判断。

## 连续结清与容量

示例：1 正在执行；2、3 排队取消并已保存终态。receivedPrefix 可以是 3，settledPrefix 仍为 0。1 的终态保存后，前缀一次推进到 3。已确认的 failed/cancelled/expired 可以结清，unknown 即使有保存终态也保留执行阻塞。

首版采用有限区间方式，不建任意乱序缓冲或历史 ID 集合。**位置只有在连续 settledPrefix 越过它后才归还区间名额。** 2、3 虽已终态确认，仍位于未压缩区间；若此时释放名额，1 挂起期间可以反复受理/取消后项，使终态集合增长。这比初稿“等终态追加结算后释放”更精确。

初始工程参数如下，可配置；实施测量若调整要同步报告，不需要负责人重新选择数字：

| 边界 | 首版工程值/策略 |
| --- | --- |
| 登记流 | 最多 16 条，每流一个稳定 epoch，不动态增加世代 |
| World 待压缩区间 | 全部 ordered 流合计最多 16 个位置；包括活动、排队、写入等待及前缀后的已结清位置 |
| 共享待执行队列 | 沿用 8 项，不含活动项；不预留来源优先级或插队 |
| 信封标签 | streamId/epoch 各 1–128 UTF-8 bytes，序号为正安全整数 |
| Event | 沿用 64 KiB 原 Event JSON 上限；信封元数据单独有界 |
| Console 身份 | admissionIds 默认 4096，只供 UserInput；同实例精确 ID 承诺保持 |
| legacy World | 独立有界身份预算，默认 4096；不占 Console 配额，不承诺长期或跨进程去重 |
| Heartbeat/请求/诊断 | 沿用 M3 已有参数；heartbeat 不占以上 World 区间 |

核对轻量性的标准是有限标量/活跃位置，而不是只有一个 Set 的代码行数。一个慢项会阻塞本流前缀，合计区间满后也会背压其他流；这是明确容量代价，暂不增加公平调度。上游发件缓冲也须有容量/磁盘政策，测试夹具明确报告；Runtime 不接管无限来源缓冲。

## 保存确认与查询

新增 World 专用投递口负责 submit、读取小型进度，以及等待某个已受理身份的保存确认。方法名称实施时与现有接口合并；语义如下：

- submit 返回 accepted/duplicate/rejected，不等待保存或处理结束。
- accepted 或活跃 duplicate 可以关联原项的保存等待；保存失败返回明确失败，不能变成“仍未确认、可以直接再次执行”。
- progress 返回登记身份、receivedPrefix、settledPrefix、nextExpectedSequence、受理开关和阻塞概要，不返回全量历史。
- 保存确认的等待归原受理项，不受诊断缓存淘汰影响。停止不取消已进入追加的结算；旧代确认若完成，只证明原身份的记录，不开启新代受理。
- 重连/重建后从小型进度查询确认前缀。旧代投递口不能向新代提交；诊断/只读查询通过当前入口取得。
- 逐项旧结果按 Session 查询；控制诊断订阅只用于呈现。读进度无写入或调度副作用，重复查询不增加长期监听器或历史常驻集合。

receivedPrefix 可供来源释放已确认事实的副本；Session 此后负责保存尚未处理事实。M4 只诊断未结清事实，不保证重启后自动完成它们。来源若需要“每条已确认事实最终都执行”，需后续恢复执行契约。

确认等级严格沿用 appendFile 完成点：追加成功后可读取，支持普通进程重建；没有 fsync、断电或外部效果事务承诺。未保存回执在内存里可以显示已取得工具结果，不能冒充保存确认。

## 单一事实依据与记录

不另设一份独立可写游标文件作为真相。来源进度是确认 Session 事实的投影，更新顺序为“追加成功 → 更新投影 → 发布确认”。投影失败关闭受理，从事实诊断/重建；不能先发确认再尝试保存。

| 记录 | 所有权与关联 |
| --- | --- |
| world_stream_registered（建议名称） | 控制记录：schema、Session/World、流、epoch、起点；不进入 Agent 上下文 |
| trigger_received | ordered World 额外携带投递身份；保留原事实、queueSequence/generation，仍无 runId |
| event/run_started/Provider/工具记录 | 携带同一投递关联及 runId，维持 M3 调用配对 |
| run_finished | 同一投递身份、可选 runId、原 RunResult；保存成功才作为结清依据 |

无需逐 tick 或逐事件另写“游标已推进”日志。排队取消无 runId 时仍有投递元组；控制记录与接收归档均排除于运行上下文。旧记录无投递身份，不能推导 receivedPrefix/settledPrefix。

首版不建持久检查点。启动可以遍历全历史，但流式读取并报告成本；之后增量维护投影。如果实测需要检查点，再把它设计为含事实位置/schema 的可验证加速信息，不把跨文件写入当作事务。

## 重建与诊断优先启动

启动阶段先打开并流式检查事实，再重建进度和阻塞诊断；完成检查后保存首次登记，然后才调用 World.start、开放通道、连接来源。starting 阶段必要控制追加也由 Runtime 跟踪；停止等待已进入写入，等待扫描/追加期间取消后不得继续启动 World。

重建不会加载全部历史 ID。根据已登记的有限流维护水位及未压缩区间，并按运行关联检查工具效果；已结束正常运行释放检查状态。非法冲突或超限历史先诊断，不为容纳损坏记录无限扩容。

| 历史状态 | 启动行为 |
| --- | --- |
| 已接收并完整结清，无阻塞事实 | 恢复前缀；来源可以继续新的 sequence，旧序号 duplicate |
| 只有接收记录，未开始或无终态 | 报未结清，保持执行受理关闭；不自动入队 |
| 有 run_started/模型记录，无完整终态 | 报中断阶段，保持受理关闭；不自动续轮 |
| tool_call 无回执、回执错配或 unknown | 报效果未知/证据不足，保持受理关闭；不补 failed、不调用工具 |
| 有终态但存在 unknown/悬空工具/必要写入缺失 | 保留阻塞；不以 settledPrefix 掩盖效果问题 |
| 登记、序号、重复记录内容或 schema 冲突 | 指出流与记录位置，不静默挑一个或跳过 |
| JSONL 尾部截断/中间损坏/读取失败 | 只读诊断，不自动修复、截断或当空历史 |

M3 legacy/Console 的未结清和工具异常同样需要诊断，不能只检查 ordered World 就宣称整个 Session 可安全执行。旧无 runId 的记录保持可读，但不能臆造现代运行分组；无法可靠关联的遗留效果标为待核对。

Session 有阻塞记录时，Runtime.start 不进入 running，模型与工具均不执行；只读诊断可单独打开。这里不新增人工“忽略并继续”按钮或状态解除操作，后续另设计明确处置证据。本阶段没有自动恢复执行。

## 有界运行视图

核心保持 JSONL 串行追加，增加流式扫描和完整运行组的有限读取能力。启动扫描 O(历史量)，运行中每触发不再读全文；明确区分启动成本和运行成本，不能把流式扫描写成常数启动时间。

首版建议存储投影保留最近成功、工具配对完整的历史运行组，初始上限 32 组/16 MiB，任一上限到达就整组淘汰。当前运行单独保留，不截断工具配对或原生 Provider 项。活动 A 的续轮只增加 A 自己的记录，不重新吸收其他排队事实/取消终态。

遇到单个历史完整组大于候选预算，不拆半组，省略该组并报告省略原因。Agent 仍对候选视图进行实际 Provider 请求体计量，保持 64 KiB 硬上限。候选窗口容量不等于模型请求容量，亦不意味着所有更早记录已消失。

为自定义 Agent 保留显式、预算化的较早历史查询能力；上下文 history 文档改为“运行事实候选视图”，不悄悄承诺全历史。默认 Agent 使用最近完整运行，旧 Agent 若依赖全文需要迁移读取方式。

启动解析按行流式读取，一条记录的缓冲和当前运行也有峰值成本。实施先采样已有合法记录、Provider 原生项及工具结果，再确定行读取/追加边界；未明确单条上限之前不得宣称整个进程具有固定硬内存上限。超限/损坏诊断不得无限保存全记录列表，只保留有限详情、计数与位置。

Runtime.trace 改为最近视图的迁移需要文档说明，建议上限 256 条/4 MiB，完整记录通过 Session 只读查询。trace 与公开诊断各自有预算；它们都不是 Memory 或来源真相。保留旧 read() 的显式全文读取用途时，注明成本，主执行与重建不调用它。

具备 ordered 基座能力的存储必须提供扫描/有界读取契约；旧自定义存储仅有 append/read 时，可以继续 legacy 用途，但不能静默退回全文件加载后声称满足 M4 有界保证。类型/API 迁移明确说明能力要求。

## 兼容迁移

- UserInput 保持既有 ID/取消/快照/回执形状，admissionIds 收束为 Console 预算；World/Console 预算分离属于配置语义变更，记录迁移。
- 新 ordered World 使用专用投递口进入同一个 TriggerChannel。现有 subscribeEvents、triggers.submit(world_event)、handleEvent 的裸 Event 路径可保留为 legacy 兼容，明确有限实例内去重且独立预算；不会自动升级为长期流。
- 选择 ordered 来源后，同一采集路径不能同时启用 legacy 与 ordered 投递，以免一事实两次受理。装配时明确选择，不自动将 legacy Event 改成新的递增序号。
- 原 JSONL 不重写，旧记录仍能只读查询和诊断。已有稳定注册的日志正常重建；旧 legacy World 历史没有上游序列映射时，不自动计算顺序水位。
- 空的新流可从 1 注册；接续已有 legacy 来源需要来源提供可信采集边界/旧事实关系，未具备则拒绝以“恢复旧流”方式开放。首版给预检报告和迁移说明，不声称核心能从任意 Event.id 逆推出序列。
- 新增记录 schema、ordered triggerId、有限 history/trace 和存储能力要求提供迁移例子；不得只增加接口后让旧调用方无提示地换含义。
- World 标识入口命名空间同时覆盖 legacy，防止任意旧 Event.id 撞上 ordered 句柄；裸 Event 形状保留，但旧调用方用 Event.id 直接 cancel/inspect 时须迁移为回执 triggerId。UserInput 标识不改变。
- 测试/样例迁移到实际新协议；M1、M3 legacy 回归保留。旧 source 文字不是登记身份，任何改名/新 Session 都不能作为核心自动去重规避路径。

## 逻辑闭环与实施组织

先定义端到端契约与迁移，随后实现一个可交互的完整离线闭环：真实来源发件记录建立稳定序号 → submit 内存受理 → 查询/等待保存 → FIFO 模型/工具执行 → 终态保存 → 连续结清 → 真正重建生产者/存储/Runtime → 重投旧序号不执行、新事实继续。

命令行演示读取确认、水位和诊断即可，不开发新 TUI 页面。故障支路另用隔离 Session 构造接收挂起、旧项阻塞后项取消、崩溃未结清和工具效果未知，展示实际记录和动作计数。

闭环成立后按来源契约/接收确认、结清/启动诊断、有界读取/迁移与综合回归组织提交。每一步写明依赖和未完成能力，不把某个局部步骤单独宣称整个基座验收。最终独立复核和负责人验收仍分别记录。

## 验收矩阵

| 场景 | 需要证明的行为 |
| --- | --- |
| 来源持久身份 | 生产者在投递前保存信封；进程重建、保存确认丢失后仍重投相同序号；没有每次 sink 新计号 |
| 长期 World | 连续事实跨越旧 admissionIds，不扩大该值；Console 预算独立；内存位置不保留全部历史身份 |
| 缺口/重复/冲突 | 乱序拒绝可补齐；重复不再记录/执行；活动内容冲突拒绝；不符 epoch/未登记流拒绝 |
| 内存与保存回执 | received 阻塞时 accepted 已返回且 Agent 未执行；保存查询不因诊断淘汰失真；失败不发成功确认 |
| 前缀与容量 | 1 挂起、2/3 取消时前缀不跨越；后项结清仍占未压缩名额；重复受理/取消不会堆无限终态位置 |
| 终态与效果 | 正常/失败/取消/过期按保存结清；unknown 即使终态保存或错误码改变仍阻塞 |
| 新进程正常启动 | 真实关闭并重建来源、存储与 Runtime，原事实 duplicate，新 sequence 能继续；不用同实例 stop/start 替代 |
| 中断与损坏 | 接收后未执行、工具声明后、效果发生后丢回执、终态缺失及 JSONL 截断均只诊断；动作不重放 |
| 启动/停止交错 | 扫描或首次登记追加期间 stop，已进入写入等待收束，World/旧投递口不迟到开放 |
| 读取窗口 | 多个历史规模下比较运行读取量、候选字节、trace、内存与启动耗时；整组/原生项/调用配对保持 |
| 自定义/旧数据 | 旧 JSONL 只读可用；legacy 有独立有限预算；存储/Agent 不支持新能力时有明确迁移/能力诊断 |
| 继承 M3 | 混合来源 FIFO、固定输入、心跳未结算名额、来源退订、unknown/存储停止与唯一终态保持 |
