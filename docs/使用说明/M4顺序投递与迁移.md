# M4 顺序投递与迁移

M4 为 World 增加稳定顺序投递、保存确认和进度重建，保持 Console、World、Heartbeat 共用 FIFO。新实例检查历史后才启动 World；未结清、工具效果未知或损坏历史只提供诊断。完整结构与验证见 [M4.0 阶段报告](../2026-10-09-M4.0进度与架构图.md)。

## 装配与来源责任

在 `composeRuntime` 或 `Runtime` 的选项中声明 `worldStreams: [{ streamId, epoch }]`，并使用具备 `scan` 的 SessionStore。World 可以实现 `subscribeDeliveries(port)`，同步接收投递口并返回退订函数。也可以由装配调用方在 Runtime 启动后取得 `runtime.deliveries`。开启顺序模式后不能同时启用 `subscribeEvents`，裸 `handleEvent`/`triggers.submit(world_event)` 会拒绝为 `ordered_required`。

登记归属于装配的 World.id 与 Agent 声明的 Session。Event.source 是领域标签，不授权新增流。首版每流只有一个固定 epoch，序号从 1 连续递增；生产者和 Runtime 重启继续使用原绑定、原 epoch 和原序号。不能通过随机 epoch、新 Session 或重新计号将旧事实当成新事实。

World 在首次投递前保存稳定身份与原事实。未保存确认、拒绝或连接中断时保留原信封；重投不修改 Event 或 expiresAt。上游已有可恢复游标可直接适配，否则需要自己的持久发件记录。Runtime 不能识别上游重新采集后分配了新身份的重复事实。

以下示例发生在已有装配和稳定发件记录的调用方中；`originalDelivery` 来自来源存储，不能在重试时临时生成序号：

```ts
const port = runtime.deliveries; // 在 start 完成后取得当前代的投递口
const receipt = await port.submit(originalDelivery);
if (receipt.status !== 'rejected') {
  await port.waitSaved({
    streamId: originalDelivery.streamId,
    epoch: originalDelivery.epoch,
    sequence: originalDelivery.sequence,
  });
  // 来源可按其存储政策释放已保存事实副本，并持久保留序列延续依据。
}
const progress = port.progress(originalDelivery.streamId);
```

`tests/fixtures/ordered-world.ts` 是真实本地 JSONL 发件记录的测试适配器，保存分配序号、原事实和确认；待确认项最多 16 个。它不是生产 World，也不为所有平台提供通用消息服务。夹具的领域值在内存中，重建 World 后重置；跨进程验证证明投递身份与核心进度延续，不证明领域状态持久化。

## 三种确认与外部效果

| 字段或回执 | 表示什么 | 不足以证明什么 |
| --- | --- | --- |
| accepted / admittedTail | 本实例占位、入队，接收追加已经启动 | 保存完成、模型已执行 |
| waitSaved / receivedPrefix | 对应接收记录追加完成，连续保存前缀推进 | 已处理、外部动作成功 |
| settledPrefix | 连续位置都有已保存终态，包括 failed/cancelled/expired | 业务全部成功、unknown 已解除 |
| ToolOutcome | World 对具体调用的效果判断 | 多记录事务、与 Session 原子提交 |

始终有 `settledPrefix <= receivedPrefix <= admittedTail`。文件确认等级为 `appendFile` 完成，没有 fsync 或断电保证。停止等待已进入的追加；旧口的保存确认只证明原投递记录，旧口不能向新代提交。

`duplicate` 返回原 triggerId 及 admitted/saved/settled 阶段，不重新入队，也不制造第二次 succeeded。活跃身份会比较原事实与有效期；语义相同的 JSON 对象键顺序允许不同。连续旧前缀只保存阶段依据，历史内容或业务结果应查询 Session。

序号缺口返回 `sequence_gap` 与 expectedSequence，不缓存、不占位；未声明流、epoch 冲突、队列满或位置满均明确拒绝。来源仍负责保存、补齐和重试；核心没有自动重试服务。

## 容量与背压

| 边界 | 默认值 / 适用范围 |
| --- | --- |
| `deliveryLimits.streams` | 最多 16 条登记流，每条固定 epoch |
| `deliveryLimits.positions` | 所有顺序流合计 16 个未压缩位置 |
| `deliveryLimits.legacyIds` | legacy World 同实例累计 4096 个身份 |
| `inputLimits.admissionIds` | 只供 UserInput，同实例累计 4096 个身份 |
| 待执行队列 | 混合来源共享 8 项，不含活动项 |
| streamId / epoch | 各 1–128 UTF-8 字节；sequence 为正安全整数 |
| 原 Event JSON | 默认 64 KiB；信封标签另行有界 |
| 历史候选窗口 | 最多 32 个完整运行组 / 16 MiB |
| Runtime.trace | 最近 256 条 / 4 MiB |
| JSONL 单条记录 | 16 MiB UTF-8，包含换行 |

位置要等连续 settledPrefix 越过才释放。例如 1 活动、2 和 3 已取消并保存终态时，3 个位置仍占用；1 结清后前缀才推进至 3。一个慢项可能使合计位置满，对其他流形成背压。首版没有来源公平调度、优先级或批处理。

上述参数可在装配覆盖，单记录上限通过 `new JsonlSessionStore(path, recordBytes)` 配置。历史、trace 和诊断视图的界限不等于整个进程硬内存上限；当前运行、模型请求、记录解析和显式全文读取都有额外成本。

## 只读诊断与启动

`runtime.diagnosis` 返回最近启动检查及实时故障概要；`await runtime.inspectSession()` 重新只读检查确认文件视图。脱离 Runtime 检查可使用根包导出的 `diagnoseSession`：

```ts
const diagnosis = await diagnoseSession(store, {
  worldId: world.id,
  sessionId: agent.declareSession().sessionId,
  worldStreams: [{ streamId: 'facts', epoch: 'source-1' }],
});
```

只读检查不会保存登记、调用 World.start/stop、启动模型或工具。`ready` 表示检查快照具备重启条件；运行中正在处理的项可能使快照显示 blocked，这不是调用方请求停止当前 Runtime。

正常 `start` 先扫描并检查来源登记、接收/终态关联、调用/回执及工具效果，再保存首次登记，最后启动 World 和开放投递。阻塞时返回 `recovery_blocked`；ordered 存储能力不足返回 `session_capability`。诊断详情最多 64 条，消息最多 1024 个字符，issueCount 保留问题计数。

未结清接收、悬空工具、unknown、必要回执缺失、登记/schema/序号冲突、文件尾截断和读取错误都阻止启动。已有终态也不能消除工具 unknown。扫描不修改、截断或补齐历史；本阶段没有“忽略并继续”、自动恢复执行或工具重放入口。

`scan` 读取本次打开后确认的文件长度，之后追加不混入该视图；按 64 KiB 块解析完整行。单写入者使用同一个 Store 追加链，多实例同时写同一个文件不在保证范围。

## 上下文与历史查询

具备 `scan` 的 Runtime 启动扫描一次，随后从已确认追加增量维护窗口。`AgentContext.history` 是最近配对完整的成功运行候选，加上当前运行事实；控制登记、排队接收和无 runId 的旧 M1 记录不进入默认候选。Provider 原生项与工具调用/回执随整组保留。超大或不完整组整组省略，不截掉半个工具往返。

`AgentContext.readHistory` 提供显式预算化查询。`{ beforeRunId, runs, bytes, includeUnsuccessful }` 可选择某运行之前的完整组，容量不得超过装配窗口上限；默认仍只选择成功组，`includeUnsuccessful: true` 才允许完整失败/取消组。查询可能扫描全历史，属于显式成本；当前活动处理的固定输入边界保持，查询不会提前交付排队事实。

ConversationAgent 继续计量实际 Provider 请求体，默认硬上限 64 KiB。候选窗口 16 MiB 不表示每次都发送这么多内容。Runtime.trace 是本实例近期已确认记录，完整归档仍在 Session；`Session.read()` 保留显式全文收集能力，有 O(历史量) 内存成本。

## 从 M3 迁移

| 既有调用或假设 | M4 处理 |
| --- | --- |
| UserInput 与 World 共用 admissionIds | UserInput 仍用该参数；legacy World 改为独立 legacyIds，ordered 使用位置预算 |
| 用原 Event.id 取消/查询 World | 使用回执 triggerId；legacy 编码也改变，UserInput 不变 |
| 裸 Event 是长期来源身份 | 兼容入口仍可用，但同实例有限，不承诺长期/跨进程去重；长期来源迁移到稳定信封 |
| 同一装配同时投递裸 Event 和信封 | ordered 模式拒绝裸 World 入口；迁移调用方与订阅后再开启 |
| SessionStore 只有 append/read | legacy 可继续，诊断为 legacy_store；没有有界重建保证，ordered 要求 scan |
| Agent.history / Runtime.trace 是全文 | history 改为候选视图，trace 改为近期视图；需要归档时显式查询 Session |
| stop/start 可继续含 unknown 的 Session | 启动检查保持 blocked；不恢复未确认效果 |
| 任意大小旧记录都可读取 | 新默认单行 16 MiB；合法超大旧记录需显式提高 recordBytes 并接受内存成本 |

原 JSONL 不重写。已保存的 legacy World 事实没有稳定序列，不能通过文件行号、queueSequence 或 Event.id 猜出来源水位；直接在这类 Session 首次登记 ordered 会被 `legacy_source_boundary` 拒绝。切换前需要领域证据明确旧处理结果、上游原序列与新来源起点；M4 不提供自动改写工具。新 Session 不继承旧 Session 的去重承诺，不能把切换当作旧事实安全重投的证明。

World 句柄由 `worldTriggerId` / `legacyWorldTriggerId` 统一编码。原 Event.id 保留业务含义，禁止猜测字符串是否已编码来混用入口。有限诊断缓存可能淘汰，保存确认不依赖缓存；旧业务结果查询归档。

## 离线验证与交互

从仓库根运行：

```powershell
node --experimental-strip-types scripts/m4-sample.ts
node --experimental-strip-types scripts/m4-console.ts
```

样例验证第一次保存并执行、重建来源和 Runtime、重复投递不调用模型/工具，以及新序号继续推进。可给 `m4-sample.ts` 提供同一目录及 `first` / `second` 参数，分两个进程运行。

离线交互命令为 `fact set answer 7`、`input get answer`、`replay 1`、`progress`、`restart`、`tick`、`diagnose`、`quit`。restart 后夹具领域值重置；replay 返回原身份阶段，不重复效果。默认手动 tick 无任务策略，不调用模型。EOF 等待已受理项结算再停止。启动被历史阻塞时仍可用 diagnose；此入口用于核心验证，不替代独立 TUI 产品。

`scripts/m4-crash-probe.ts` 由集成测试在临时目录执行接收保存、效果发生、终态保存三个退出窗口；`scripts/m4-profile.ts` 记录规模、归档、视图和启动扫描成本。它们均使用离线脚本模型和本地测试 World，不连接真实服务。

## M5 控制记录补充

可选任务功能在同一事实链增加 task_changed / task_claimed，任务状态不改变 World 来源序号与结清条件，未启用任务的 M4 样例保持原行为。新任务日志需要 M5 读取端；原 M4 日志无需转换。任务重建、存储能力和版本边界见 [M5 任务与心跳延续](M5任务与心跳延续.md)。
